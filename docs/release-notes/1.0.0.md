## Nothing destructive by default

The largest change is one you should not be able to see, because it stops
things happening.

Every rule in every policy now requests `WARN` and declares `destructive:
false`. That is not a coincidence of the current rule set; it is a property the
test suite asserts on every run. A policy that requests a Tier 3 action fails
CI.

Actions are now on an explicit four-tier ladder:

| Tier | Name | Examples |
| --- | --- | --- |
| 0 | Observe | record the finding |
| 1 | Notify | `WARN` |
| 2 | Restrict | `REVOKE_ACCESS`, `QUARANTINE`, `DISABLE`, `THROTTLE` |
| 3 | Destructive | `DELETE`, `TERMINATE` |

Every path that acts on a resource — the scheduler, the dashboard, the MCP
tools — goes through one function, `resolve_effective_action()`. A Tier 3
action requires all five of these to be true, and any single failure downgrades
the action one tier and records why:

1. The rule's metadata declares `destructive: true` and names the tier.
2. `ENFORCEMENT_ENABLED` is on. It ships off, including on fresh installs.
3. The workspace is named in `DESTRUCTIVE_ACTION_WORKSPACES`.
4. A human approved this specific run, within the approval window.
5. The run is under the blast-radius limit.

Tier 2 actions are reversible by construction. Each one captures the prior
state as an undo payload and writes it to the audit table *before* the change is
applied, so an action that fails halfway can still be rolled back. The dashboard
has an undo button on every executed action.

Irreversible SDK calls are confined to one module,
`providers/databricks/destructive.py`, and a test reads the source of every
other module to keep it that way.

## The policy assistant

Four things, on the AI Gateway:

- **Draft** a rule from a plain-language description. The result is validated
  with `opa check` before you see it, and it is checked for tier and
  destructiveness by code that does not consult the prompt. The assistant can
  write Tier 0–2 and nothing else; a Tier 3 policy has to be written by hand in
  a reviewed pull request.
- **Plain English** — every policy has a sibling `.md` explaining it, rewritten
  on save, so the human-readable version cannot drift from the Rego. It always
  opens with the consequence, so a reviewer who skips the Rego still sees an
  escalation.
- **Pull request notes** with the blast radius filled in from the most recent
  scan. Any tier escalation is rendered first, under its own heading, and the PR
  title is prefixed.
- **Ask** — a chat panel that answers questions about your policies and
  findings. Its tools are read-only by construction: none of them import a
  resource handler.

## Scanning

- Workspaces are scanned concurrently, with bounded concurrency and per-
  workspace timeouts, rather than one at a time.
- A workspace that fails now says so. An authentication failure, a resource type
  that could not be enumerated, and an evaluation that never completed each
  record a finding and mark the run partial, instead of reporting zero
  violations — which reads exactly like a clean estate.
- Scheduled runs record their real counts. The worker had been reading a field
  the scan engine no longer returns, so every scheduled run was filed with zero
  violations regardless of what it found. It now runs through the same engine as
  a manual scan, and one failed run no longer stops the schedule.
- Findings are stored in their own table, with the requested action, the
  effective action, and the downgrade reason as explicit columns. The dashboard
  paginates on the server and filters over facets computed from the run.
- Passing checks are recorded, not just violations, so a rule with no findings
  can be told apart from a rule that never ran.
- OPA runs as an embedded server with `--watch`, evaluated over a pooled HTTP
  client, which is roughly twenty times faster than the CLI path it replaces.

## Policies

The nine thematic policy files are now fourteen per-resource files —
`clusters.rego`, `jobs.rego`, `sql_warehouses.rego`, and so on. Each rule
carries an ID, category, owner, severity, and description in `rule_metadata`,
and each file carries package annotations. The Policy Editor shows all of it,
plus git history for the file and a playground.

Old policy names still resolve, so existing allowlist entries keep working.

## Policies are stored in git, and only in git

The Policy Editor no longer has a Save button, and this is a fix rather than a
removal.

Saving used to write the file to the server's disk. The app runs on a platform
with an ephemeral filesystem, so that edit lasted until the next restart and
then disappeared — with no error, and no way to tell it had happened. A policy
you believed you had changed would quietly revert to the old version, still
enforcing the old rule.

Now there is one way a policy changes: **Open PR**. It cuts a branch, commits
your Rego, commits a freshly generated plain-English `.md` next to it, and opens
a pull request. Both files land in the same diff, so a reviewer who does not
read Rego can still see a rule go from "warns the owner" to "revokes access".
Retiring a policy is a pull request too — it stops a rule enforcing everywhere,
which deserves the same review as changing one.

While you are still working, your edit is kept in your browser as an
**unsubmitted draft**. It survives a refresh, a closed tab, and switching
between policies, and the editor shows you it is there with a Discard button. It
is deliberately local: a change nobody has reviewed is not yet a policy.

The directory the scanner evaluates is now a working copy of your target branch,
rebuilt at startup and every five minutes, with a Refresh control in the editor.
That means a merged pull request takes effect without a redeploy, and a retired
policy actually stops being evaluated. The editor shows which branch is being
evaluated and how long ago it synced, so "I merged the fix but it still flags"
has a visible answer.

Running against a local checkout is unaffected — the sync detects it and leaves
your working tree alone.

### Discarding a working-copy edit

When the policies directory is a git checkout, a policy edited outside the app
shows a warning, because the working copy is what a scan evaluates — an
unreviewed edit there means the estate is judged against a rule nobody saw. That
warning now carries a "Discard local changes" button that restores the file to
the last commit, so the remedy is no longer a shell.

It acts on one file at a time, on purpose: a blanket restore would take
unrelated work with it.

## Settings

Configuration now resolves in three layers: in-code defaults, then environment,
then a database-backed store an admin can edit in the UI. Anything that changes
what the system will do to a resource is in a Danger group and needs a typed
confirmation — including the scheduled scan mode, which is the only setting that
acts with nobody watching. Enabling enforcement is logged with the name of the
person who did it.

A scheduled run never carries an approval, because there is no one present to
name. Raising its mode widens what it may do as far as Tier 2; destructive
actions stay out of reach from the scheduler by construction.

The scan schedule itself is now editable here too. Previously only the *mode* of
a scheduled scan was, which meant a danger-gated setting governed a feature you
had no way to switch on — turning scheduling on at all required an environment
variable and a redeploy. You can now set the cron expression, the workspace, and
the environment, and the page shows you the next three times a schedule would
fire before you save it. An expression that does not parse is refused on save
rather than accepted and quietly ignored, which is what used to happen: a typo
left the scheduler idle and said so only in a log.

Changes take effect within a minute, with no restart. The worker re-reads the
schedule as it runs, so saving one arms it and clearing one stops it.

The GitHub connection is editable here as well, in its own section: the access
token, the repository, the branch pull requests are opened against, and the
directory the `.rego` files live in. Connecting the Sentinel to a repository, or
moving it to a different one, no longer means editing an environment file and
redeploying. The GitHub client is built per request, so a saved token works on
the next pull request you open.

The token is write-only. It is stored server-side and never sent back to this
page — the field tells you whether one is configured and shows its last four
characters, which is enough to tell two tokens apart without putting either in a
browser. To replace it, type a new one over it.

The repository, branch, and directory are treated as safety settings and need a
typed confirmation, because between them they answer the question *which rules
govern this estate*. Pointed at another repository, the next sync replaces every
policy in the working copy with that repository's, and the following scan
enforces rules nobody here reviewed. Pointed at an unprotected branch, the review
step between an edit and enforcement quietly disappears. A repository that is not
an `owner/name` pair is refused on save rather than accepted — GitHub answers a
mistyped repository with a 404, which reads like a permissions problem and sends
you looking at your token instead of your typo.

The page is now split into sections with their own navigation — Enforcement
safety, Scanning, Agent, Notifications, Branding, and the action ladder — rather
than one long scroll. Each section shows how many of its settings have been
overridden away from the deployment defaults, so you can see what has been
changed without opening all of them. Safety comes first in the list and is the
section you land on.
