## The editor leads with the agent

There were two agent panels, Ask and Draft, and neither could do the other's
job. Asking Draft a question got you a policy back, because its prompt said to
reply with a fenced Rego block and nothing else, and anything outside the fence
was discarded before it ever reached the screen.

They are now one panel. It answers in prose, and when an edit is warranted it
proposes one. A proposal arrives as an inline diff — the same red and green you
would see in a code review — rather than a wall of text you have to compare by
eye. Applying it goes through validation and a pull request exactly as before.

The code editor is hidden by default and the agent panel takes the width it used
to share. The code is one button away, and it reveals itself automatically when
a proposal arrives, which is the moment it matters. If you would rather always
see it, the setting is remembered.

`Cmd`/`Ctrl+Enter` sends a message. `Shift+Enter` starts a new line. Plain
`Enter` still sends, so nothing you were already doing has changed.

## Plain English writes itself

The Explain button is gone. The tab generates its explanation when you open it,
and regenerates when the policy changes.

Explanations are cached by the content of the policy rather than its name, so an
explanation is generated once for a given policy body and then shared by
everyone who looks at it. Editing and undoing an edit costs nothing.

This also fixes a quiet bug. A committed explanation was compared against
itself, so it always looked current — including when the editor held a draft
that said something different. It is now compared against the committed policy,
so "this explanation is out of date" appears when it is true.

## Exceptions can cover a class of resources

An exception used to mean one resource, and it waived *every* rule that fired on
it. Granting a pass on an idle cluster also quietly excused that cluster's
missing tags and its access mode.

There is now a second kind. A class exception waives **one rule, for one
resource type, in one workspace** — "unattached clusters are expected in the
sandbox workspace" — and nothing else. It cannot be widened.

Because a class exception covers resources that do not exist yet, two things are
required rather than optional:

- **An expiry date.** A permanent class-wide waiver is a policy change without a
  pull request. Class exceptions must end, and the date must be in the future.
- **A rule and a resource type.** A blank selector matches nothing. It never
  means "everything", the same way an unrecognised action never means "go
  ahead". There are dedicated tests on this, because it is the single place in
  this feature where a mistake would silently switch off a policy.

The exceptions list now shows how many findings each exception is currently
hiding, so a broad waiver is visible rather than quiet, and it says so before
you delete one.

The resource type list on that page was also wrong. It offered `table`, which is
not a type anything scans, and omitted six types that are.

## Testing Center

A new page that answers the question "does this rule actually fire on the thing
I think it fires on", without scanning anyone's real estate to find out.

A fixture is one resource plus the rules that should and should not fire on it.
Running it uses the real policies, real OPA, and the real action ladder — only
resource discovery is replaced. No workspace is contacted, and there is nothing
in this path that could contact one.

Results distinguish four kinds of disagreement, because they do not mean the
same thing. A rule that was expected to fire and did not is the serious one: on
a dashboard, a policy that never fires is indistinguishable from an estate with
nothing wrong in it.

You can also capture fixtures from a real scan. Every finding already stores a
snapshot of the resource it was evaluated against, so a captured fixture is by
construction the shape the Databricks API actually returns, rather than the
shape someone remembered while writing JSON. Owner email addresses are replaced
on the way out.

The same page runs the Python test suite and shows the failures with their
messages.

## Two bugs this found

Building the fixture runner immediately caught a rule that had never worked.

`CTL-CLU-002` checks whether a cluster has a compute policy attached, and it
asked the obvious way: `not input.resource.policy_id`. In Rego, JSON `null` is a
defined value, so that expression is false when `policy_id` is null — and null
is exactly what the SDK returns for a cluster with no policy. The rule was
silent on every cluster it existed to catch, and reported a clean bill of health
while doing it. The same mistake was in the SQL warehouse policy. Both are
fixed, there is a shared `is_set` helper so the next policy does not repeat it,
and a fixture now pins the behaviour.

Separately, the CI step that runs the safety suite pointed at a directory
containing nothing but an empty `__init__.py`. The real suite is elsewhere.
That step now runs the 75 tests it was always supposed to.
