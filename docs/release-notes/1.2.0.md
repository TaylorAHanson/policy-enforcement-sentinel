## The problem this release is mostly about

Rego does not complain when a rule reads a field that was never collected. The
expression simply fails to match. The rule never fires, every resource of that
type is reported compliant, the dashboard is green, and nothing anywhere says
otherwise. It is a false negative that is invisible from the outside and
permanent.

That is not hypothetical here. Ten policies in this repository have a staleness
rule gated on `idle_days`, and no handler has ever collected `idle_days`. They
were written, reviewed, merged and shipped, and not one of them has ever fired
or ever could. They are indistinguishable, from any screen in this application,
from rules that looked and found nothing wrong.

Once the catalogue existed it was possible to ask the question properly, and the
answer was worse than ten. Of the 64 shipped rules, 41 could not fire against a
real workspace. Most of them can now; the ones that still cannot say why, and
for several of them the reason is not something more code will fix. The full
breakdown is below.

So the vocabulary is now published and checked.

**Every handler declares the fields it collects.** Thirteen resource types, each
listing what discovery actually sets and what it means — including the honest
entries, like Apps and Lakeview dashboards having no tags at all, which is what
stops someone writing a tagging rule for a resource type that cannot have tags.

**The assistant is told the vocabulary before it writes anything.** Ask for a
rule that needs data nobody gathers — "put an app in STOP if it has been unused
for 24 hours" is the example that prompted this — and it now says so, names the
missing field, and explains that the app handler would have to collect it during
discovery first. It offers the nearest rule that can be written instead. It no
longer writes the rule anyway.

**Validate reports it.** A policy reading an uncollected field gets a warning
that is deliberately not an error: the file compiles, and blocking a save would
be wrong when the annotation is simply out of date. But it is stated plainly,
next to the compile errors, in the words that matter — this compiles, and it can
never fire.

**Proposals carry the same warning.** A change from the assistant that reads
data nothing collects arrives with the warning attached to the diff, before you
take it.

`GET /policies/schema` returns the whole catalogue if you want it programmatically.

## Testing, in the editor, on the draft

There is a Tests tab in the Policy Editor now, and it runs against what is in
the editor — not the committed file. Testing the merged version of a policy you
are halfway through changing answers a question nobody asked, and answers it
with a green tick.

It also reports coverage, which is the number people forget to ask for. A rule
no fixture exercises is not a passing rule, it is an untested one, and on a page
of green ticks the two look identical. The Testing Center says so at the top of
the page now, above the results, for the same reason.

Coverage is reported in both directions. A rule only ever seen firing has never
been shown to leave a compliant resource alone, which is how a rule that is too
broad gets through review.

## A fixture cannot testify about data that does not exist

The fixture set went from seven files, all clusters, to 71 across every resource
type that has a handler. That part is unremarkable. What it turned up is not.

A fixture builds the policy input document directly, bypassing discovery, so
nothing stopped one setting a field no handler collects. All seven original
fixtures set `idle_days` that way, and one asserted that an idleness rule
*fires* — a rule that cannot fire against any real workspace. It passed on every
run. Coverage counted it. That is worse than no test at all, because a green
tick gets read as evidence.

So fixtures are now checked against the same field catalogue policies are, and
coverage counts two different things: rules with a fixture, and rules shown
firing on data the scanner can really produce. When those numbers disagree, the
Testing Center leads with the gap and names the fixtures responsible. A test
asserts that the shipped set has no such fixture, so this cannot come back.

Fixtures also declare `workspace_type` explicitly. It used to be inferred from
whether the workspace *name* contained the word "enterprise", which nothing told
the person writing the fixture — so rules scoped to enterprise production
quietly failed to fire and looked unreachable when they were merely untested.

## "41 rules have no fixture" was a true sentence that helped nobody

It named the mechanism instead of the problem, and it reported one number where
there were several separate situations with different people who could act. The
Testing Center splits them, because the split is the actionable part — and the
split is what made the rest of this release possible. Once each rule said *why*
it was not working, most of them turned out to be fixable, and the ones that
were not turned out not to be an engineering problem at all.

The classification is derived, never stored, so a handler that starts collecting
a field moves every rule waiting on it without anybody maintaining a list.

**Splitting the categories immediately found a bug the earlier pass missed.**
`SEC-VOL-001` tests `storage_type in {"dbfs", "local_volume"}`, and the volume
handler only ever emits `MANAGED` or `EXTERNAL` — the same value-mismatch shape
as `SEC-CLU-001` and its `"shared"` access mode. It had been sitting in the
undifferentiated pile of 41.

## Then most of them got fixed

45 of 64 rules are now shown firing on realistic data, up from 23. Two things
got them there, and neither was writing more tests.

**Twelve fields that were already sitting on objects the handlers fetch.**
`scale_to_zero` and `inference_logging` were on the served-model config the
serving handler already had in hand. `owner_type` for jobs and pipelines comes
from `run_as` — and it is worth being precise that this is *run-as*, not
*creator*, because a job somebody built and correctly pointed at a service
principal is fine and must not be flagged. `entitlements` and `roles` were on
the SCIM record. `is_published` on a dashboard, `capacity_units` and tags on a
Lakebase instance, `path` and `in_git_folder` on a notebook. The notebook
`is_scheduled` flag needed one extra pass over the workspace's jobs to see which
paths any task actually runs; the whole notebook policy was inert before it.
Column descriptions come from one `information_schema.columns` aggregate per
catalog rather than a call per table.

**Six rules whose logic could not match.** Five were the same bug wearing
different hats: `CTL-DSH-002`, `CTL-DST-007`, `CTL-LKB-004`, `CTL-SPN-003` and
`CTL-VOL-004` all tested `not object.get(resource, "owner", false)`, which is
only true for a missing key. Every handler defaults `owner` to the string
`"unknown"` precisely *because* the API named nobody — so five rules whose
entire job was finding unowned resources reported that everything had an owner.
There is a `common.no_owner` helper now, alongside `common.is_set`, and it knows
all four shapes absence arrives in.

`SEC-CLU-001` compared `access_mode` to the literal `"shared"`, which the SDK
has never emitted for any cluster. Its description says the concern is users
being "indistinguishable in audit logs", so it now tests the modes that actually
lack isolation — `NONE`, `LEGACY_PASSTHROUGH`, `LEGACY_TABLE_ACL`,
`LEGACY_SINGLE_USER_STANDARD`. `USER_ISOLATION` is deliberately not among them:
it is what the UI calls Standard, it keeps users apart, and it is the mode this
rule wants people to move *to*. A fixture exists solely to stop the next person
widening the rule to include it.

## Idleness is not one thing

Nine rules asked for `idle_days` as though every resource had one, and the
honest answer turned out to be that three do.

A cluster states it outright: `terminated_time`, with a running cluster idle for
zero days by definition. A job's last run is one small call, and jobs get
`failed_consecutively_days` from the same call — measured from the oldest
unbroken failure, so a job that failed for a month and was then fixed reports
nothing. A table has `last_altered`, which is worth labelling carefully: that is
silence from upstream, not disuse. A reference table read by every query in the
building and updated once a year looks identical to an abandoned one, which is
why the rule warns rather than acts.

Apps, dashboards, Genie spaces, Lakebase instances, service principals and SQL
warehouses publish when they were *changed* and nothing about when they were
*used*. An app's `update_time` is when it was last deployed. A rule that treated
that as usage would flag every stable, heavily-used app in the estate. So those
six collect nothing, and where the value is unknown the field is left off the
resource entirely rather than defaulted to zero — absence lets the rule stay
quiet and lets the diagnosis say the field was never collected, where a
placeholder would make an unanswerable question look answered.

## Some rules are not waiting on us

This is the part that changed how the whole thing is reported.

The remaining rules split into two groups that had been lumped together as
"waiting on the scanner", which was wrong and quietly expensive — it pointed at
an engineer and implied the work was merely queued.

**Ten rules need access the scanner does not have.** Six are the `idle_days`
rules above: the real answer for them is `system.access.audit` and
`system.query.history`, and reading those needs `SELECT` on the `system` catalog,
which only a metastore admin can grant. Three want Unity Catalog grants, and
this one is a trap worth spelling out: `information_schema.table_privileges`
looks like exactly the right source and is filtered to the caller. Unless you
own the object, own its catalog or schema, or are a metastore admin, you are
shown **only your own grants** — and Databricks documents a further limitation
where even `MANAGE` holders see only theirs. A scanner reading that would get
back a near-empty result, no error, and conclude that nothing in the estate is
over-shared. An earlier draft of this release collected it. It was removed,
because a security rule that reports clean because it is blind is worse than one
that admits it cannot see.

**Four rules read something Databricks does not publish at all.** A pipeline's
expectation count lives in the event log of a run, not in the pipeline
definition. There is no data-quality result surface on a table, no
connection-utilisation metric on a Lakebase instance, and nothing that scans
notebook source for credentials.

The distinction now has its own two categories, its own tone in the UI, and each
affected rule names the specific access that would unblock it. **Zero rules are
merely waiting on a collector** — a test asserts it, so a new rule reading a
field that *could* be discovered and has not been will fail the build rather
than join a backlog.

## What is left

- **45 rules** are shown firing on data the scanner can really produce.
- **10 rules** need a grant, each naming which one.
- **4 rules** read something the platform does not expose.
- **4 rules** govern `workspace`, which has policies and no handler.
- **1 rule** is still probably broken: `SEC-VOL-001` asks whether production data
  sits in DBFS, and the volume handler discovers Unity Catalog volumes, which are
  `MANAGED` or `EXTERNAL` and never DBFS by construction. That is not a value to
  correct but a question about a resource class nothing discovers, and it needs a
  decision rather than a patch. It stays visible until it gets one.
- **0 rules** are simply untested.

The fixture set is 71 files across every resource type with a handler, up from
seven all-cluster ones, and every fixture is checked against the field catalogue
before it is allowed to count as evidence.

## The field catalogue is now checked too

Everything above rests on `discovered_fields` being true. Policies are validated
against it, a fixture using a field outside it is refused, the assistant is
prompted from it, and the coverage panel decides a rule is workable by consulting
it. It is the root of the whole arrangement and it is a hand-written docstring on
a Python class. Nothing had ever checked it against a real workspace.

That gap is worse than the one this release opened with. A field declared and
never actually collected does not merely leave a rule dead — it leaves the
diagnosis reporting that rule as **working**, because the diagnosis reads the
same declaration. The bug acquires an alibi.

So a scan now records what the handlers really emitted, as counts per resource
type and field with no resource surviving into the aggregate, and the Testing
Center compares that against what the handlers claim. Three disagreements are
reported: a field declared and never set, a field set and never declared, and a
rule comparing a field against a literal the estate never produces.

The third earns its place. Pointed at the current fixtures it independently
recovered both value mismatches found by hand this release — `access_mode`
against `"shared"`, and `SEC-VOL-001`'s `storage_type` against `"dbfs"` — without
being told what to look for. A test now pins `SEC-VOL-001` as the one known case,
so the next one to appear fails the suite rather than hiding behind it.

A fourth situation is reported separately and quietly: a field that is declared,
collected, and empty on every resource in the estate. No rule reading it can
fire, and that may be entirely correct, because a nullable setting on a feature
nobody uses is indistinguishable from a collector that has broken. Calling that
drift would have been the easy mistake — the first draft did exactly that and
flagged `autoscale_max_workers` on a fleet where nothing autoscales. A report
that cries wolf about correct behaviour is a report people learn to close.

The check needs a real scan. Run against fixtures it would only confirm that
fixtures were written to match the catalogue, which is true by construction and
proves nothing, so the panel says plainly that it has nothing to report yet
rather than showing a green tick it has not earned.

It then said exactly that through two real scans which had recorded the
observations perfectly well. A scan stores a summary per workspace and writes
the observations inside each one; the reader looked for a single aggregate at
the top level, found nothing, and reported that no scan had happened. A line
further on it referred to a column the run model does not have, which never
raised because the loop never reached it.

Both were in the seam rather than in the logic. `observe` and `reconcile` had
twenty-one tests between them and were correct; nothing exercised the path from
a stored run to a rendered report. The seam is now covered, including the case
that made the merge necessary — a field set in one workspace and absent from
another is collected, not missing, so the aggregates are added up before being
judged rather than reconciled one at a time.

Worth stating plainly, because it is this module's own subject one level up: the
check reported *nothing to see* while the evidence sat one key away. Failing in
the reassuring direction is the exact fault it was built to catch.

Against the real estate it now reports two disagreements and twelve inert
fields. The inert list is the more interesting half: `tags` is empty on every
resource of every type in the estate, so every rule keyed to a cost-centre or
owner tag is structurally unable to fire, and `entitlements` and `roles` are
both empty on every service principal, which leaves the `account_admin` fix
above still waiting on data.

## Four rules that were dead and are not any more

These were fixed because the data was already being collected and the policy was
looking in the wrong place — no new discovery, no behaviour invented.

`CST-PIP-001` and `CST-PIP-005` read `input.resource.attributes.serverless` and
`.continuous`; the pipeline handler sets both at the top level. `CTL-LKB-002`
read `retention_days` while the handler collects `retention_window_days`, so it
compared the default zero and flagged *every* production Lakebase instance —
a false positive on all of them, now correct.

`CST-CLU-004` tested `autotermination_minutes == 0`, but discovery reports a
disabled autotermination as either `0` or `null` depending on how the cluster
was made, and the null case slipped through — the same mistake `common.is_set`
was added to fix for `policy_id`. Both forms now fire, with a fixture each.

`CST-MSE-001` deserves its own mention because it failed in the opposite
direction. It read `attributes.custom_tags.cost_center` through an object no
handler has ever built, and a path through a missing object makes `not` true —
so instead of never firing, it fired on *every* serving endpoint in the estate
regardless of how carefully it was tagged.

## Policies are a list, and the editor is somewhere you go from it

The way to reach a different policy used to be a picker in the editor's header —
a control sitting beside a title that implied the page was about the file
already open, and which people did not find. A dozen policies is a collection,
and a collection wants a list.

So `/policies` is now a dashboard: every policy, what it governs, how many rules
it has, how many findings it produced in the last scan, and who last changed it
and why. Editing one opens `/policies/<name>.rego`, which means an open policy
is now something you can link to and something the back button understands —
neither of which was true when the selection lived in memory.

It is one request. The alternative was a metadata call, a history call per
policy and a facets call, so fourteen policies meant sixteen round trips before
the first row appeared; the per-policy git history is now one `git log` pass
over the directory rather than a subprocess per file.

**The list says which policies cannot fire.** Four rules govern `workspace`, and
no handler discovers a workspace, so those rules never run against anything.
Until now that showed up as zero findings, which is the same number a policy
gets when the estate is clean. The row is marked, and the page says which policy
and why, because those two zeros mean opposite things.

## Creating, renaming and retiring a policy

All three open a pull request. There is deliberately no path from this page to
the policies directory — the second way in is always the one that skips the
checks.

**New policy** produces a draft, not a file. It comes back as a complete,
compiling Tier 1 policy with the METADATA block, the `rule_metadata` map, the
`applies` guard and one real rule that reads only fields the handler for that
resource type actually collects. An empty editor meant the first several
validation attempts were about scaffolding rather than about the rule you
wanted. Only resource types a handler discovers are offered, and a type that
already has a policy says so.

**Rename is not a file move**, and this is the part worth reading. A policy's
name is stored in allowlist exceptions, saved filters and historical findings.
Moving the file alone orphans every one of them, and it does it silently: an
exception that matches nothing simply stops suppressing, which reads as the rule
getting stricter rather than as a broken reference.

So one pull request does three things — writes the file under the new name,
rewrites the `package` declaration to match, because OPA resolves rules by
package and a mismatched declaration would leave the policy loaded under its old
name regardless of what the file is called, and records the old name in the
policy's own `custom.replaces` metadata so stored references keep resolving.
Rule IDs never change, so anything naming a rule directly is unaffected.

That alias lives in the policy rather than in a lookup table in application
code, which means it travels with the file through the normal sync and takes
effect when the pull request merges instead of when the app is next deployed. A
policy renamed twice keeps redirecting from both of its old names. A live policy
always wins over an alias, so taking a retired name back does what you expect.
The dialog states all of this before you commit to it.

## "Add a rule" now exists, and is honest about what it does

The rules list had no way to add to it, which invites the question even though
the answer is not a button. A rule is a Rego expression, and the interesting
part — which fields to test and how — is exactly what a form cannot capture.

But "you cannot add a rule here" is also false. So the button is there and does
the thing that actually works: it opens the Assistant with the request already
started and the policy's resource type filled in, because the first thing the
assistant needs to know is which handler's fields are available, and a request
that omits it produces a rule reading data nobody collects. What comes back is a
diff you review, same as any other proposal.

## The editor gives the work its width

Metadata is the first tab again, with the Assistant second. Its rules list has a
search box and a category filter once a policy has four or more rules — datasets
has ten — and clicking any rule's category chip filters to it. Searching matches
rule IDs, names, descriptions and severities, and the word "destructive" finds
the rules worth worrying about even though it appears in none of their text.

When the code is showing, the divider between it and the panel beside it drags.
Double-click it to even the two up. Where you leave it is remembered.

## History shows what changed

Picking a revision used to open a short, fixed-height block of the whole file
with no way to close it again. It is now a searchable list of commits, and
choosing one opens a diff against what you have in the editor — because the
question people bring to history is what changed, not what the file looked like.
The whole file is one click away, the panel uses all the height available, and
there is a close button.

## One button for exceptions

The two buttons — "One resource" and "A rule for a class" — were a fork in the
road presented before anyone had the context to choose. There is now one "Add an
exception" button, and the choice is the first thing inside the dialog, with
each option stating what it actually costs. The narrower one is selected by
default, and choosing the class-wide one fills in the mandatory expiry date
rather than rejecting the form afterwards.

## Capture wrote two tests that could not pass

Capturing tests from a real scan produced two files that failed the moment they
were run, and both were the capture's fault rather than the policies'.

The first was self-inflicted in an interesting way. Anonymisation replaces an
owner's email address before a fixture reaches the repository, and it treated
any non-empty owner as an address. Discovery writes the string `unknown` for a
resource whose owner it could not determine, and that is not a person's name —
it is precisely the condition the no-owner rules exist to catch. So the capture
recorded "`CTL-VOL-004` fired here", then rewrote the unowned resource into an
owned one, and shipped a test asserting that the no-owner rule fires on a
resource with an owner. Only an address is now replaced.

The second was an identifier collision. Resource ids are unique within a type,
not across the estate, and this workspace has `regression-validation-dev` as
both an app and a Lakebase instance. Capture grouped findings by id alone, so
the two merged into one file: the app's resource document carrying the union of
both resources' expectations, asserting that four Lakebase rules pass against a
resource type they never run on. Captures are now keyed by type and id, and the
type is in the filename, because names collide as readily as ids do.

Both are now pinned by tests. Worth noting that the failure was visible and
specific — the harness said `missing=['CTL-VOL-004']` and
`not_evaluated=['CST-LKB-001', ...]` — and that both bugs were in the machinery
that writes the tests rather than in anything being tested. A capture tool that
quietly produces unpassable tests would train people to ignore red.

## The Testing Center reads as a report rather than an error

The page had four full-width alert blocks at equal weight, and the loudest of
them was the one that mattered least right now. "45 of 64 rules have been shown
to work" is a standing measurement that moves about once a week, and it was
rendered as a red block with a cross on it, which reads as *something just
broke*. Meanwhile the thing that had actually just happened — two tests failing
out of ninety-seven — was a badge in the corner.

It is now ordered by how fast things change rather than by how much detail they
carry. The result of the run you just asked for is at the top, with the failing
tests named and a control to hide everything that passed. Coverage is one line
that folds open, with the rules that look broken hoisted out of the fold,
because that is the only part of it anybody can act on from this page. The
conditions the results were produced under — enforcement off, catalogue
unchecked, captured tests sitting uncommitted — are one quiet line at the
bottom instead of three competing alerts.

The fold caught one more instance of the original complaint on its way in. With
the panel dropped inside a row labelled "45 of 64 rules proven", its own
headline — "45 of 64 rules have been shown to work", in a red box, above a
paragraph restating the same breakdown — put the same number twice in two
phrasings, one line apart. It now renders without its frame or its headline when
something above it already states the count.

Two different denominators were most of the confusion. Ninety-seven tests and
sixty-four rules are different units, and showing them as peers invites the
reader to work out a relationship that was never stated. The page now says what
a policy test is before showing any numbers.

They are also called policy tests rather than fixtures throughout. A fixture is
the input half of a test and the word is accurate, but only to somebody who
already knows the harness, and the people who most need this page are the ones
who do not.

## A finding is now a thing rather than a row

The dashboard could only ever answer one question: what is wrong. On this estate
the answer is 3,789 violations, of which 3,038 have been byte-identical across
every scan since the first one and exactly one is new. Nobody triages a
four-digit list that has not moved in a month — everything in it looks equally
urgent and equally old, so none of it gets looked at.

The cause was that a finding had no identity. Every scan appended a fresh row
per resource per rule, and nothing connected that row to the same problem seen
last time. Five scans of one workspace had produced 39,264 rows describing about
3,800 facts, and "has this been open since May or did it appear this morning"
was not answerable from any of them.

Findings now have a stable identity — workspace, resource type, resource id,
rule — and a lifecycle: first seen, last seen, last *evaluated*, occurrences,
and how many times it has closed and come back. The append-only log is untouched
and remains the evidence; this is an index into it, derived, and rebuildable
from the log alone.

The identity includes the resource type rather than hanging it off the id,
because ids are unique within a type and not across one. Yesterday's capture bug
was exactly this mistake, and the same workspace would have triggered it again:
`regression-validation-dev` is both an app and a Lakebase instance.

### Closing one is the whole difficulty

A finding that is absent from a scan has not necessarily been fixed. It can be
absent because the rule ran and passed, because the resource was deleted,
because a policy was narrowed so the rule no longer applies, or because
discovery could not enumerate that resource type at all. Only the first is good
news and the last is not news at all.

Collapsing those into "resolved" would mean that a permissions change breaking
the volume handler silently closes four hundred findings and reports it as
remediation. That is the same shape as the `field_reconciliation` bug above — a
check failing in the reassuring direction — except that here the reassurance is
the product's primary output. So nothing closes without positive evidence, a
scan may only judge resource types it actually enumerated, and the three ways a
finding can close are recorded and displayed separately.

A finding that could not be judged keeps its previous status *and* its old
`last_evaluated` stamp, which is what makes staleness visible. Without that,
"open" means both "confirmed still true this morning" and "nobody has been able
to look since March", and an interface that cannot tell those apart is
presenting stale data as current.

### What it shows

The dashboard leads with the delta and demotes the standing total to context.
Against the real history the panel opens with one finding appeared, none
returned, none fixed — which is the honest state of this estate and fits on one
line, where the same information previously required reading 3,789 rows.

The table is backfilled from the runs already stored, so the trend exists
immediately rather than after two more scans. Replaying this workspace's twelve
runs dates 3,038 findings to the first scan and 751 to the following morning —
the 751 being what the twelve dead rules fixed earlier in this release turned
out to have been hiding.

### The panel follows the run you select

First cut of this panel always described the newest scan, while the stat cards
directly beneath it described whichever run was selected in the scan history.
Selecting an older run put two correct numbers about two hundred pixels apart,
disagreeing, with nothing on screen saying they were answering about different
scans: the panel reading "3,789 findings are open in total" above a violations
card reading "3,041".

Worse on the newest run, where the two agreed exactly — that agreement teaches
you they are meant to match, which is what makes the later disagreement read as
a bug rather than a difference in scope.

The panel now takes the selected run, and is labelled when that is not the
newest. It also no longer states a total at all: the violations card owns that
number, and a second total at a different scope beside it was the collision.
The one date format the panel had been mixing with `8/4/2026` is now used
throughout.

The panel also follows scans as they finish. It read its run once on mount, so a
scan would complete, the run table and the cards would update around it, and it
would sit there describing the scan before — right until somebody reloaded the
page.

Most of what the panel reports is a fact about a finished scan and reads the
same today as it did that morning. Two exceptions, both because this table holds
each finding's current position rather than an event log. Staleness is only
asked of the newest scan — "nothing has confirmed this lately" is a claim about
now, and asked of a scan from March it would report the entire estate, truthfully
and uselessly. And a past scan's *fixed* count reports only what is still true:
a finding fixed at scan 8 that came back at scan 9 no longer counts toward scan
8, because reopening clears the record of which scan closed it. That
under-reports how much a past scan moved and cannot over-report it, and the
newest scan is exact. Making it exact for every scan means storing a row per
finding per scan, which is not worth it to correct history nobody is acting on.

## Captures are local now, and promoting one is a decision

Capture writes a policy test from a real scan. It is the most useful kind of
test in the project, because a hand-written one drifts from what the Databricks
API actually returns and a drifted test proves a rule works against a shape that
does not occur. Every dead rule found this release turned on exactly that:
`storage_type` arriving as `"VolumeType.MANAGED"` where the rule compares
against `"dbfs"`, `autotermination_minutes` arriving as `0` rather than absent,
`access_mode` arriving as an enum. None of that is guessable.

It is also a resource document from somebody's production estate, named after
their catalogs and volumes. One of the twenty-five sitting in this working copy
was `captured_storage_scentre_group_raw_data.json`, in catalog `psk`.

Both facts have the same cause, and they were being traded off against each
other because captures landed in `backend/fixtures/synthetic/` — the committed
directory. They sat untracked in the git panel, one `git add .` from being
published, and every commit meant judging twenty-five files by hand.

They now land in `backend/fixtures/captured/`, which is gitignored. Capture is
consequently a safe thing to press: it cannot leak and it cannot clutter the git
panel. Both directories are loaded when tests run, so a capture is still a test
that executes locally, which is the reason for taking one. Coverage counts the
shipped set only — otherwise the number is higher on the laptop that took the
captures than anywhere the app is deployed, and a figure that changes with who
is looking at it is the sort of thing this page exists to stop.

### Promotion keeps the shape and drops the names

Testing → Promote scrubs a capture and writes it into the committed set, named
for the rule it demonstrates rather than for a resource. What survives is
everything that makes a capture worth having: the exact enum spellings, the
nulls, which keys arrive at all. What goes is the identity.

Three things make it something to trust rather than something to hope about.

It checks its own work. The list of identifying keys is a guess written against
today's handlers, and the next handler will emit a key nobody added to it — so
after scrubbing, promotion looks for any word it set out to remove, anywhere in
the result, and refuses if one is still there. It fails closed and names the
field, rather than writing the file and noting the problem somewhere nobody
reads.

It checks that scrubbing did not change the answer. Replacing names edits the
document the policies read, so a rule matching a naming convention evaluates
differently afterwards — and the failure mode is a test that still passes while
no longer demonstrating anything. The scrubbed copy is run before it is written
and compared against what the capture recorded.

It refuses to vouch for a rule that does not work. A capture records what the
policies did, so a broken rule appears as a rule that passed. The first capture
promoted here asserted that `SEC-VOL-001` passes — the rule that cannot fire at
all, on the very resource type that proves it. That expectation is dropped
rather than the promotion refused: the test keeps everything it genuinely shows
and says nothing about the broken rule, which leaves the rule visibly untested,
which is true. A green tick gets read as evidence, and manufacturing one for a
dead rule is the failure this whole harness exists to prevent.

Structure is preserved where it is load-bearing. A Unity Catalog id is
`catalog.schema.name`, and scrubbing it as one opaque string turns it into
`id-1`, discarding a property any rule splitting an id on dots would depend on.
An address is replaced with an address, whatever key it arrived under. Sentinel
values like `unknown` are left alone, because replacing one with a valid-looking
address turns an unowned resource into an owned one and inverts the no-owner
expectation the capture was taken to record — the capture anonymiser's own bug,
fixed yesterday, which had every opportunity to come back here.

### The test suite no longer depends on cloud credentials

The unit suite took fifty seconds on one machine and fifteen minutes on another,
which read as a flaky hang. It was not flaky. `scan_workspaces` builds a service
per workspace before calling the method the test had faked, and that constructor
builds a real `WorkspaceClient` — so one test was doing live OAuth against three
workspaces. With a token cached the SDK returned immediately; without one it
waited five minutes per workspace and then failed on a timeout unrelated to
anything the test asserts.

That test now bypasses the constructor, as the rest of the file already did. And
because the failure mode was a stall rather than an error, the unit suite now
refuses to build a real client at all: an accidental one fails in about a second
with a message saying so, instead of stalling and only on machines without
credentials.

## Known, and not fixed here

The field checker finds problems in thirteen of the shipped policies. Fixing
them means deciding what discovery should start collecting, per resource type,
which is a larger piece of work than adding the check. The current state is
recorded in `backend/tests/unit/services/test_resource_schema.py` so it is
visible and can be driven down deliberately.

Two are worth calling out. Every `idle_days` rule described above is inert. And
`CTL-WHS-00x` on SQL warehouses tests `policy_id`, which the warehouse handler
does not collect — so unlike the others it fails in the opposite direction, and
flags every production warehouse.

`SEC-VOL-001` is unfixable by editing the comparison. It asks whether production
data sits in DBFS, and it runs against objects returned by the Unity Catalog
volumes API, all of which are in Unity Catalog by definition. The rule needs a
decision about what it is for — retire it, or repoint it at external volumes,
which is a real governance question but a different one — and it stays visible
until it gets one.

Anonymisation covers owner addresses and nothing else. A captured test keeps the
resource's real name, and names carry information — catalogues and apps in a
real estate are called things like `scentre_group_raw_data`, which identifies a
customer to anyone who reads the repository. That is a deliberate trade for now,
because a fixture with its name scrambled is much harder to reason about, but it
means captured tests need reading before they are committed rather than after.
The capture note in the interface says so; it is not enforced.

Twelve rule fixes from the previous session were absent from the commit that was
supposed to carry them, having been reverted in the working tree beforehand, and
have been restored. They are listed in the commit that restores them. Worth
noting because the Policy Editor's revert control calls `restore_from_head`,
which discards uncommitted work for one file with no confirmation and no undo;
that is a sharp edge nobody has filed down yet.
